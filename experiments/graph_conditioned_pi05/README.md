# Graph-conditioned pi0.5 proof of concept

This experiment compares two rollout systems while preserving the fixed RoboTwin task and evaluation protocol:

- `visual_only`: the original instruction, images, and robot state.
- `visual_retrieved_graph`: a graph-aware hierarchical rollout that uses deterministic current-frame task state to issue compact phase instructions, protect a held object, and interrupt stale action chunks when task-relevant relations change.

## Frozen protocol

Both conditions must use the same task configuration, episode seeds, pi0.5 checkpoint, camera images, robot state, action representation, nominal action-chunk horizon, and evaluation criteria. The graph-aware treatment is intentionally a system-level intervention: it may derive compact instructions from current graph state, interrupt the unused remainder of a nominal chunk after a task-relevant graph event, replan at that event boundary, and clamp the active gripper closed while transporting an object known to be held. These mechanisms are part of the treatment, not controlled variables. Results therefore estimate the utility of the complete graph-aware planning system relative to the standard visual-only rollout; they do not isolate the causal effect of graph prose alone. Report success, hard-success, collision, and collision count/category metrics, together with prompt phases and chunk-interruption counts.

Retrieval is one-hop from target objects and robot effectors. It includes only true relations whose evidence-validity mask is true, uses `countertop_camera` for camera-conditioned facts, and excludes redundant inverse edges by default.

The current treatment uses event-driven replanning within the nominal 50-action horizon. During grasping, it preserves the original task instruction exactly. Its model-server call path is also identical to visual-only: unchanged grasp chunks skip tokenizer fitting and prompt rewrites, and only inference advances the deterministic policy RNG. After every executed action, the graph-aware controller still observes valid task predicates. A new grasp immediately discards the unused actions, switches to compact placement guidance, and latches only the active arm's gripper closed during transport. Release readiness is distinct from strict goal completion: a conservative gravity-assisted gate may start release, while the actual `in` or `on` relation remains the goal signal. Tasks without exactly one target and one destination retain their base instruction.

The live model server uses the checkpoint tokenizer and enforces the complete prompt limit for post-grasp phase guidance. Retrieved node declarations and general relation prose are deliberately excluded from this baseline treatment.

Submit the paired 10-seed control/treatment array with `evaluation/submit_paired_10.sh`. When an unchanged visual-only baseline does not need to be rerun, submit only the same 10 graph-conditioned seeds with `evaluation/submit_graph_10.sh`. The graph-only wrapper creates ten array tasks indexed `0-9`, records `condition_mode=graph_only`, writes `pi05-graph_<job>_<index>.out` logs, and stores results only under `visual_retrieved_graph` in a timestamped `*-graph-only` batch directory. After each array task's result directory is found and validated, `slurm_paired_eval_task.sh` also renders `episode0_with_prompt.mp4` beside `episode0.mp4` via `evaluation/render_prompt_overlay.py` -- the original rollout on the left, a per-frame panel on the right showing frame index, phase, substage, held arm, and the exact prompt text the policy received, updating in sync with playback. This is a debugging aid, not part of the evaluation result: a render failure only logs a warning and never fails the task.

For the diverse benchmark campaign, run `evaluation/submit_diverse_5x10.sh`. It covers d10 clutter in office (`put_mouse_on_pad`, `put_book_on_book`), study (`put_cup_in_box`), kitchens (`put_spoon_on_plate_ks`), and kitchen-large (`put_sauce_can_in_basket`). If any task has fewer than ten expert-validated seeds, a five-task precollection array expands its task-specific bank first; an `afterok` coordinator then submits five paired arrays, for 100 policy episodes total. Pairing is exact within each task. Seed banks are task-specific because a simulator seed that admits a valid expert plan for one task need not admit one for another.

After the paired visual-only baseline has been established, use `evaluation/submit_diverse_graph_5x10.sh` for graph-only iterations. It uses the same five tasks and validated seeds but submits five 10-task graph arrays (50 episodes total), stores `condition_mode=graph_only` in the campaign job table, and does not rerun visual-only.

Expert action nodes, action outcomes, and future annotations are prohibited policy inputs. Current pi0.5 rollouts do not create equivalent online high-level action nodes, so action history is disabled in both conditions. Exported action nodes may be used only for offline analysis or labels after rollout.

The present HDF5 episodes validate alignment and input construction; four successful episodes are not sufficient for a statistically meaningful policy comparison. Simulation-derived ground truth can also overstate real-world graph quality. Later evaluation must preserve validity/confidence metadata and test sensitivity to perception, depth, calibration, occlusion, and temporal noise.

## Phase 3 live pi0.5 adapter

The dual-environment evaluator reads graph state from every live observation. `visual_only` executes the standard pi0.5 action chunks with the original task instruction. `visual_retrieved_graph` uses simulator evidence as an oracle task-state interface for a `grasp → placement → release` controller. In `graph_delta_orientation_align_v27`, annotated grasps without validated contact retain the strict 1.5 cm lateral-centering requirement. V27 adds an explicit `orientation_align` stage for nearby annotated arms outside the 20-degree orientation band, while preserving the unified `grasp_approach` stage for orientation-compatible arms regardless of height alignment. Two consecutive target-contact observations from the same arm, while height and orientation remain aligned and lateral error is at most 1.8 cm, validate contact and enter CLOSE immediately; a one-frame contact cannot use the relaxed threshold. V27 retains the V26 grasp and release thresholds. V26 retains the V25 5 cm release clearance and reduces the validated-contact lateral allowance from 2.5 cm to 1.8 cm. V25 increased the `in`-destination release clearance from 2 cm to 5 cm. Historically, V23 permitted release once the safely aligned target bottom is at most 2 cm above the destination AABB rim; this replaces the uncalibrated requirement to descend 2 cm below it and matches the task’s XY-based success semantics. The final-descent prompt now asks the object to reach the basket rim rather than go below it. The experimental V22 raw, single-frame contact-conditioned 2.5 cm threshold was reverted after it caused premature, unstable closure. V24 reintroduces 2.5 cm only after two consecutive aligned contact frames; all non-contact closure retains 1.5 cm. V21 introduced straight-down final-descent language; V23 updates `in` tasks to request motion without sideways drift until the object reaches the rim, while `on` tasks request the same controlled descent until surface contact. V21 changed language only; V23 deliberately changes the `in`-task release threshold as described above. Low-level action controls remain unchanged. V20 removes standalone `left` and `right` tokens from VLA-facing legacy simulator-name fallbacks; explicit semantic labels and internal identity remain intact. Alternate-arm blockers remain internal arm-selection evidence and are not included in the VLA prompt; collision language is reserved for the active arm. The v17 grasp behavior is: grasp has one stable near-target `grasp_approach` intent rather than independent height and forward-motion substages. Once an orientation-compatible arm is within the 12 cm vicinity, the prompt is `Approach the middle of <target> with the open <arm> gripper. Keep moving toward it until the gripper is centered for grasping.` Height or distance fluctuations inside that vicinity therefore do not change the prompt or discard the remaining action chunk. The controller still deterministically holds the selected gripper open until strict close geometry passes the 1.5 cm gate or persistent aligned contact passes the V26 1.8 cm gate; close remains a bounded, verified latch. Outside the vicinity it retains the collision-aware align instruction. V18 changes placement only: it first aligns the held target over a footprint-safe destination interior, then lowers it, and permits release only after the relation-specific descent gate passes. Grasp and the 50-action nominal planning horizon are unchanged. There is no no-motion timeout; rollout termination is governed by the full episode step limit (or success). V15 extends the annotated approach before close: the local-axis entry boundary moves from −1.2 cm to +0.5 cm.

The `graph_delta_target_relative_approach_v17` treatment selects an arm only when exactly one validated straight target corridor is clear and every alternative corridor is blocked. Outside the 12 cm vicinity it says `Align the <arm> gripper with <target>.` Inside that vicinity, every non-close geometry uses the single stable `grasp_approach` instruction; signed height, distance, and approach-axis error remain evidence and close guards but no longer select different language substages. The grasp-height reference prefers the actual world height of each arm's own expanded grasp-pose family (`LiveGraphContext.left_reference_grasp_positions_m`/`right_reference_grasp_positions_m`) over the object's AABB top surface: for a tall object the true grasp point can sit several centimeters from the top surface, and the old AABB-top reference required a wide, purely-compensatory tolerance just to paper over that systematic mismatch. Height, distance, and horizontal offset are now all derived from the SAME single candidate in that family: the nearest candidate within the 20-degree orientation-compatible band (not independently selected position and orientation hypotheses). Height is aligned if the TCP is within tolerance of that nearest candidate's height; when it isn't, the correction direction (up/down) follows that same candidate. The control reference retains the annotated contact pose and local approach axis but deliberately uses a contact-calibrated 5 cm TCP standoff instead of copying `get_grasp_pose`'s 12 cm planner seed. Across v6/v7 live traces, physical target contact repeatedly occurred 6--8 cm beyond the 12 cm reference along local approach X, so the planner seed was not the physical gripper-center close point used by these observations. Each arm's height family is not just the one unrotated -5cm point, either: `create_target_pose_list` rotates that point's position as an offset from the raw annotated contact center (not a self-rotation of the point itself) through the same per-arm `rotate_lim` arc used for orientation, so the candidate's height can move by up to roughly `5cm * sin(rotate_lim range)` -- roughly 4cm for a ~1 radian arc -- well beyond the ±3cm tolerance; treating every arc candidate as sharing the unrotated seed's height, as an earlier version of this treatment did, was wrong by exactly that amount. Because the swept range (`rotate_lim`) is itself arm-specific in RoboTwin, the height reference is exactly as arm-specific as the orientation reference, not shared between arms. Each arc candidate's sign is also resolved the way `create_target_pose_list` itself resolves it, not always the configured `+theta`: it computes the `+theta` candidate first and, if that candidate's position ends up on the wrong side of the contact center (a negative dot product against `towards=[0,-1,0]`, `GRASP_TOWARDS_AXIS`), discards it and recomputes the whole candidate -- position and orientation together -- from `-theta` instead; an earlier version of this treatment always used the configured `+theta` directly, which can select a candidate RoboTwin's own search would never generate and move a 12cm-offset candidate's height by several cm, the same order of magnitude as the position-vs-orientation bug above. An unresolvable/unannotated actor falls back to a single candidate built from the object's own (x, y) and the target AABB's upper surface for z (or the object's own pose height if no AABB is available) -- height's reference is the same one used before this treatment existed, at this treatment's wider ±3 cm tolerance rather than the pre-treatment ±2 cm band; distance and horizontal offset now share that exact same fallback point too, rather than falling back to the raw object pose independently of what height just fell back to. For annotated targets, close requires valid height, at most 5 cm total joint-candidate error, and local approach-axis error from +0.5 cm to +2.0 cm, and local lateral error at most 1.5 cm; target contact bypasses approach-axis and total-distance gates but not lateral centering. Unannotated targets retain the v3 10 cm distance ceiling. Height and orientation now gate CLOSE through one coherent joint pose candidate; position-only and orientation-only views remain diagnostics for comparison. Every effector's world-orientation error against the target's annotated grasp-contact-point orientations is computed and exported every frame; v5 uses the 20-degree compatibility band to select a coherent control candidate and withholds geometry-specific substages when that band is empty. Each reference orientation reproduces RoboTwin's own contact-to-grasp rotation (`get_grasp_pose`'s fixed, exactly-120-degree remap of the raw annotated contact pose) applied to the object's static contact-point geometry directly, not the planner-dependent `get_grasp_pose`/`choose_grasp_pose` call path itself, so this involves no motion planning and is safe to evaluate every frame; comparing against the raw, untransformed contact-point pose instead would silently check against a reference ~120 degrees from the one RoboTwin itself targets. A contact-point matrix is validated (finite, a proper orthonormal rotation block, a valid homogeneous row) before any of this runs, and the conversion itself never raises: `transforms3d`'s quaternion conversion does not validate its input on its own -- it raises for a non-finite matrix (which would otherwise crash live evaluation on a single bad annotation) and silently returns a plausible-looking but meaningless quaternion for a reflection or other degenerate matrix (which would otherwise read as an ordinary, seemingly-valid reference orientation). A malformed contact point is skipped like an absent one; if every contact point on an actor is malformed, the whole reference reads as `annotation_invalid`, not `available`. The error is measured against each reference's full mechanical-equivalence family, not the bare reference alone: RoboTwin's own `create_target_pose_list` searches a per-arm `rotate_lim`-radian arc (read live from the embodiment config, e.g. 0-1 radian for aloha-agilex) about the reference's own jaw-closing axis when looking for a reachable grasp, and the gripper's two fingers are symmetric under a 180-degree flip about the approach axis, so both are folded into the comparison rather than penalizing a mechanically-identical grasp as if it were misaligned. The flip is composed after each rotated arc candidate, not applied to the seed before rotating -- 3D rotations don't commute, so the two orders produce different orientations for any nonzero arc angle, and only the former actually represents "this specific candidate's own finger-swapped variant." The arc is sampled at exactly RoboTwin's own `ROTATE_NUM=10` candidate count and half-open grid (`step * i` for `i` in `range(10)`, matching `create_target_pose_list`'s own indexing) rather than an evenly-spaced inclusive grid: RoboTwin's own search never reaches the arc's upper endpoint, so including it would credit an orientation as aligned that RoboTwin itself never generates, artificially shrinking the reported error near that boundary. The configured `rotate_lim` order is preserved rather than sorted ascending: `create_target_pose_list` uses the signed step `(rotate_lim[1] - rotate_lim[0]) / ROTATE_NUM` directly, so a hypothetical reversed config walks from `rotate_lim[0]` toward (but never reaching) `rotate_lim[1]` regardless of which is numerically larger -- moot for every embodiment config in this repo today (all ascending), but sorting first would silently swap which endpoint is excluded if that ever changes. Because `rotate_lim` is itself arm-specific in RoboTwin, each arm gets its own fully-expanded reference set (`LiveGraphContext.left_reference_orientations_wxyz`/`right_reference_orientations_wxyz`) rather than one set shared between arms -- for aloha-agilex specifically both arms' `rotate_lim` happen to be numerically equal, but the two tuples remain genuinely separate so this stays correct for embodiments where they differ. One thing is deliberately not reproduced, flagged rather than silently assumed: `choose_grasp_pose`'s arm-mirrored preferred-direction scoring (`GRASP_DIRECTION_DIC["top_down_little_left"/"top_down_little_right"]`, blended with a task-specific side preference) used to rank candidate contact points per arm before reachability filtering -- a soft preference over which contact point RoboTwin would rather use, not a hard validity boundary like the symmetries that are reproduced (`create_target_pose_list`'s `towards` sign disambiguation, described above alongside the height reference, is now one of those reproduced behaviors, not a gap). Because a resolved-but-empty reference is indistinguishable from a broken one unless it says why, the trace also carries `orientation_reference_status` (`available`, `target_unresolved`, `actor_unresolved`, `annotation_missing`, `annotation_invalid`, or `extraction_error`) and `orientation_reference_count` alongside `orientation_reference_available`. `actor_unresolved` (the target's name resolved but no wrapped Actor could be found for it) is kept distinct from `annotation_missing` (the actor resolved but has zero annotated contact points): the former points at the actor-lookup logic itself as a possible bug, the latter at a genuine, benign fact about that object, and conflating them would let a lookup bug masquerade as an ordinary unannotated object. A batch where actor resolution silently fails the whole time reads as 100% `target_unresolved`/`actor_unresolved`/`extraction_error`, not as a quiet, indistinguishable string of NaNs that could pass for "this task has no annotated objects." A real diagnostic batch confirmed that position-only readiness could select a candidate 40--174 degrees away from the gripper while an orientation-compatible candidate was materially farther away. In v5, annotated control therefore uses the joint-best candidate: nearest in 3D among candidates within 20 degrees; when no candidate is within that band, CLOSE and geometry-specific substages are withheld and the controller returns to generic ALIGN. Unannotated objects retain the position fallback and fail open as before. V17 retains the unified approach state and changes only its wording to a target-relative approach and deliberately removes the v11 directional final-approach language from live selection: all orientation-compatible non-close states inside 12 cm remain in the unified grasp approach, validated contact still enters close immediately when laterally centered, while geometry-only annotated readiness must persist for two consecutive observations; the prior 8--10 cm persistence behavior remains only for unannotated fallback. Close says `Close the <arm> gripper to grasp <target>.` Once authorized, v10 overrides only that arm's gripper channel closed for a bounded 15-action attempt, preventing prompt noncompliance or transient pose noise from cancelling physical closure. A still-valid pose receives at most one additional bounded attempt; validated `held_by` plus held-arm contact ends the latch and advances normally, while failure returns to a geometry-selected corrective approach. Provisional validated holds keep closure active through the three-frame acquisition debounce, after which the placement latch takes over without an intervening open action. Candidate arms are evaluated independently so invalid-height contact cannot mask a geometrically ready arm. A collision warning is added only when the nearest validated blocker's AABB is within 20 cm of the blocked end-effector. Action chunks are truncated to the remaining episode-step budget. No no-motion stall detector is active; the episode step limit is the sole timeout. V18 subsequently replaces this placement behavior with the destination alignment and descent gates described above; the v17 grasp behavior in this paragraph remains unchanged. General stall recovery, approach-arm latching, and gripper-frame lateral alignment are deliberately deferred to later isolated treatments, pending the diagnostic data this version collects. Height and distance readiness are now measured against the SAME reference joint pose, fixing both mismatches this treatment previously had: `target_vertical_offset_m`, `target_horizontal_offset_m`, and `target_distance_m` all come from the nearest orientation-compatible candidate in the arm's expanded grasp-pose family. The independently position-best and orientation-best candidates remain trace diagnostics only. `target_horizontal_offset_m` (that same candidate's x/y-plane offset) is exported alongside them, diagnostics-only for now. Before this fix, distance was `norm(target_object_pose - TCP_pose)` -- distance to the object's own pose/center -- while vertical offset already used the grasp-pose family; for an object whose annotated grasp point sits well off-center (tall or asymmetric geometry, or simply a side contact point far from the object's own origin), that let a TCP holding a fully height- and orientation-aligned grasp pose still read as "not close enough," because the distance metric was silently checking against a different point than the one height had just confirmed was reached. This is not a theoretical concern: a live batch (seed 40002 in `graph_delta_annotated_grasp_height_reference_v3`) stalled for 300+ frames at 10.36cm object-center distance -- 3.6mm past the close ceiling -- while height and orientation were aligned essentially the entire time, because the annotated grasp point on that object sat roughly 10cm+ horizontally from its own pose center. V17 retains the v15 annotated closure calibration separately from the unchanged unannotated fallback: annotated candidates use the 5 cm total-distance, +0.5 cm to +2.0 cm local-approach, and 1.5 cm lateral gates above, while `GRASP_CLOSE_MAX_DISTANCE_M` and `GRASP_CLOSE_PREFERRED_DISTANCE_M` continue to govern objects without annotated grasp geometry.
The action trace exports three candidate views per arm: position-best and orientation-best are diagnostics-only, while joint-best is the v5 control reference. Joint-best first restricts candidates to orientation error at most 20 degrees and chooses the nearest in 3D; when that band is empty it reports the minimum-orientation candidate, and when orientations are unavailable it reports the position fallback. Each view includes the original annotation contact-point ID, arc sample, finger-flip variant, pose, signed world/local TCP error, distance, orientation error, selection status, and frame-to-frame identity changes.


Node labels prefer an explicit catalog `semantic_label`. When the semantic label merely repeats a legacy simulator name, known infrastructure prefixes (`task_`, `target_`, `object_`, `model_`), trailing numeric instance IDs, and standalone `left`/`right` tokens are removed before separators become spaces. Removing directional tokens is a temporary prompt-layer compatibility hack for actor names such as `basket_right`: those suffixes encode simulator identity rather than reliable camera-relative directions. Explicit semantic-label overrides are preserved. The future fix is to publish unambiguous semantic labels in the benchmark catalog and delete this legacy-name exception. Object identity never depends on this display label: stable IDs and aliases distinguish duplicate labels.

Each `_episodes.jsonl` record retains success/collision metrics and adds the condition plus graph inference counts, selected/dropped node and fact averages, tokenizer-measured graph tokens, and destination-seed availability.

Destination IDs are read only from `TASK_ENV.get_role_names()`; expert action nodes are never consulted. Singular and multi-destination tasks export concrete scene IDs. Tasks whose destination is not stored in a `des_obj*` attribute opt in with `benchmark_destination_attrs`; generic attributes such as `basket_right` are never inferred globally because the same object may be a source in another task. Older task metadata that only provides destination names is resolved against the object catalog only when the match is unambiguous; otherwise evaluation fails instead of guessing. Tasks with no destination role fall back to target-and-effector seeds and record `destination_seed_available: false`.

Graph-token counts use the exact checkpoint tokenizer. The logged full-prompt count is explicitly an estimate because pi0.5 discretizes the normalized state during its internal transform, while the server-side preflight receives raw state. The model's normal truncation guard remains authoritative. A future refinement can expose normalized-state token accounting without duplicating the full image preprocessing transform.

The current adapter intentionally supports the recommended dual-environment evaluator. A full rollout requires the local pi0.5 environment and checkpoint, which are not present in this checkout, so this checkpoint is validated through syntax, launch dry-runs, synthetic live snapshots, and the schema-1.9 episodes.
